## What this is

POS / inventory / sales system for a single company (Distribuidora Arango), built on CodeIgniter 4.7 over MySQL database `distribuidora`. It replaced a custom-framework PHP app (same database, same schema) that was retired and deleted on 2026-11-03; a zip of that code and DB dumps are in `C:\laragon\respaldos\`. Spanish UI, code comments in Spanish.

Local URL: **http://distribuidora.test** (Laragon, Nginx vhost `C:\laragon\etc\nginx\sites-enabled\distribuidora.test.conf` — a manual, non-`auto.` file that listens on 80 and 8080 because Laragon's global port is 8080).

## Scope

Web (dashboard, ventas/POS, cotizaciones with PDF and public `/c` link, inventario, compras, traslados, conteos, lotes, alertas, clientes, reportes, configuración, usuarios, bitácora, apps), PWA `/m` and REST API `/api/v1` (63 endpoints). The `mantenimiento` module has a manifest but no routes/controllers (it was never installed in the legacy DB) — porting it means recovering its code from the backup zip.

Unknown routes go to `Errores::noEncontrado` (Routing `$override404`): JSON 404 under `/api/`, redirect to `/login` without session, otherwise a 404 page inside the layout.

## Architecture

- **Modules** — `app/Modules/{name}/manifest.php` (sidebar menu, `menu_order`, `depends`) + optional `routes.php` (receives `$routes`). `App\Libraries\ModuleManager` loads routes of modules installed in the `modules` table, in `id` order, and builds the sidebar (`core` `menu_top`/`menu_bottom` around the rest). All manifests are present so the menu is complete even for unported modules.
- **Filters** (`app/Config/Filters.php`): `auth` (redirect `/login`, 401 JSON for `/api/*`), `sucursal` (puts `empresa_actual`, `sucursal_actual`, `sucursales_disponibles`, `deposito_actual`, `depositos_disponibles` in session via `SucursalService::contexto()`, recalculated on every request), `movilauth` (redirect `/m/login`, 401 JSON for `/m/api/*`), `permiso:a,b` (passes if the user has any of the listed permissions). Group filters are **merged** with route filters (CI4 `RouteCollection::create`), so `permiso:` on a route inside an `auth,sucursal` group keeps both. Global `csrf` except `api/v1/*`; global `secureheaders`.
- **CSRF** — session-based, field `_csrf_token`, header `X-CSRF-TOKEN`, `regenerate = false` (POS does many AJAX posts). Every POST form needs `csrf_field()`; JS uses `csrf_hash()`. JSON callers should send `X-Requested-With: XMLHttpRequest` so a bad token returns 403 instead of a redirect.
- **`App\Libraries\Auth`** — same static API as legacy (`check()`, `can()`, `rol()`, `attempt()`...). Django pbkdf2 + bcrypt passwords; TOTP 2FA for `gerente`/`auditor`/`superadmin`. Permission matrix: `app/Config/Permisos.php` (`superadmin` gets everything).
- **`App\Libraries\Db`** — thin static wrapper over `db_connect()`: `row()`, `all()`, `value()`, `insert()` (returns id), `update()`, `begin/commit/rollback()`. Legacy SQL uses `?` placeholders, which are CI4 bindings too, so queries port verbatim. `numberNative = true` in `.env` makes MySQLi return native ints/floats like the legacy PDO did — needed because libraries use `strict_types`.
- **Business logic** lives in `app/Libraries`, shared by web, POS and PWA:
  - `VentaService::procesar()` — invoice number, ITBMS, payments (`ventas_pagos`), credit limit, kardex, FEFO lots. Caller wraps it in a transaction. Items without `deposito_id` use the session's active depot (fixes the legacy bug where web POS sales never reduced stock).
  - `InventarioService::registrar()` — the only way stock changes: updates `inventario.existencia` and writes `inventario_movimientos`. `descontarLotesFefo()` for `maneja_lotes` products.
  - Product codes: `ProductoService::siguienteCodigo($empresa, $categoria)` = category prefix + next 3-digit number (`ALI158`). Prefix = the one most of the category's products already use (≥5 and ≥50%, letters only), else first 3 letters of the category name (`REP`, `LUB`), `PRO` without category. The create form fills it via `GET /api/inventario/siguiente-codigo?categoria_id=` and `guardar()` generates it if left empty.
  - `ProductoService` — replaces the legacy DDD layer (Register/Update/Delete/AddStock use cases + repositories): create with prices, per-depot stock and auxiliary units; update; delete (cleans inventario/precios/unidades, refuses if the product has kardex movements); `agregarStock()` with weighted average cost. Initial stock and manual stock now go through the kardex (legacy wrote `existencia` directly).
  - Movement types are the DB enum: `entrada`, `salida`, `ajuste`, `traslado_salida`, `traslado_entrada`. Legacy used `traslado_out`/`traslado_en`, which the enum rejects — transfers never saved in the old app. Physical-count adjustments write `ajuste` rows directly with explicit saldo (InventarioService treats `ajuste` as an outflow).
  - `CajaService` (migration `2026-11-08-000001`) — cash register per cashier and branch: `cajas` (monto_inicial, cierre with `arqueo` JSON = per payment form esperado/declarado/diferencia + bill count) and `caja_movimientos` (entradas/salidas). `ventas.caja_id` / `cobros.caja_id` are set inside `VentaService::procesar`, `CotizacionService::convertir` (`CajaService::paraVenta()`, throws if `companies.exigir_caja` and no open register — default on; `$ctx['omitir_caja']` only for the data generator) and `CobroService::registrar` (never blocks). Expected cash = initial + cash sales + cash abonos + entradas − salidas; CREDITO is reported, not counted. Web `/caja` (own), `/cajas` + `/cajas/{id}` (history/printable, gerente can close someone else's), PWA `/m/caja`; `BaseController::render()` injects `caja_actual`/`exigir_caja` for users with `caja.usar` (top bar chip, POS chip + blocking open modal `cajas/_aviso_abrir`). Permissions: `caja.usar` (cajero, supervisor, gerente), `cajas.ver` (supervisor, gerente, auditor), `cajas.gestionar` (gerente). SMA (Stock Manager Advance v4, Laravel/Vue, in Downloads) is used only as a feature reference — pending from that list: gastos, ventas en espera, devoluciones parciales, estado de cuenta, reporte por vendedor, etiquetas, importar, envío por correo.
  - `CobroService` (migration `2026-11-06-000001`) — abonos de clientes a ventas a crédito: `cobros` (recibo `REC-nnnnnn`, forma de pago, tienda) + `cobros_ventas` (a qué facturas se aplicó). Parciales o totales, a una factura o a las más antiguas primero; baja `clientes.saldo_pendiente` y pone la factura en `pagada` al llegar a 0. Pendiente de una factura = su CREDITO en `ventas_pagos` − lo aplicado. `VentaService::anular()` rechaza facturas con abonos; `VentaController::registrarPago` (botón "pagar" web) cobra lo que falta vía este servicio. UI móvil en `/m/cobrar`; aún sin pantalla web de abonos parciales ni reporte de cobros.
  - **Saldos anteriores** (`SaldoAnteriorService`, migration `2026-11-09-000002`): credits clients owed before the system. Table `saldos_anteriores` (`SA-000001`, fecha, monto, referencia, estado `pendiente|pagada|anulada`) — **not** ventas, so they never touch inventory, caja or sales reports. They raise `clientes.saldo_pendiente`; `CobroService::pendientes()` merges them with credit invoices (rows with `venta_id = null`, `saldo_id`, `numero_factura = SA-…`, oldest first) and `cobros_ventas` now has nullable `venta_id` + `saldo_id`. One by one from the client detail tab "Saldos anteriores" (`POST /clientes/{id}/saldo-anterior`, `clientes.editar`; anular only without abonos, `clientes.eliminar`) or from Excel at `/clientes/saldos-anteriores/importar` (button in cuentas por cobrar): template = one row per active client; match by ID → código → exact name (ambiguous name = error), unknown name creates the client, optional "Límite de crédito" updates it, same client+monto+fecha already loaded = "Ya cargado" (re-uploading doesn't duplicate).
  - **Presentaciones** (`productos_unidades`: docena, caja, paca… con `factor_conversion`): el inventario siempre está en unidades base. `ventas_detalle` guarda `unidad_id/unidad_nombre/factor` (migration `2026-11-06-000002`; `cantidad` va en la presentación vendida) y `VentaService::anular()` repone `cantidad × factor`. PWA: `/m/vender` elige presentación y admite cantidades decimales (peso); `/m/inventario` (📦) crea/quita presentaciones; `/m/pedido` pide en bultos (por defecto el mayor, se puede cambiar) y `/m/compras/{id}` recibe contando en bultos; ambos envían unidades base al servidor.

## REST API (`/api/v1`)

- **Auth**: `POST /api/v1/login {username|email, password, codigo_2fa?}` → `data.token`; then `Authorization: Bearer <token>`. `users.api_token` stores only the SHA-256 of the token (`ApiTokenFilter::hash()`), `users.api_token_expira` = login + 30 days (`expires_at` in the login response); a new login replaces it, `POST /api/v1/logout` revokes it, deactivated users are rejected. Roles in `ROLES_2FA` with TOTP enabled must send `codigo_2fa`. 10 failed logins per IP / 15 min → 429 (counter in cache).
- **No PHP session**: `ApiTokenFilter` loads the user into `Auth::usarUsuarioApi()`; `Auth::check/id/rol/can()` and `AuditService` read from there instead of `session()`. API controllers extend `Api\ApiController` (not `BaseController`, which would start a session). Context: user profile's empresa/sucursal, default depot = main depot (endpoints accept `deposito_id`, validated against the branch and the user's allowed depots).
- **Permissions**: every route has `permiso:` from the same matrix as the web (legacy API checked none). Exceptions handled in code: `PUT usuarios/{id}` (self or `usuarios.gestionar`).
- **Responses**: `{status: success|error, message, data|errors}`; 401 bad/missing token, 403 permission, 404 JSON for unknown `/api/*` paths (`Errores::noEncontrado`), 422 validation/business errors.
- **Prices are server-side**: `ventas/procesar` and `cotizaciones` take `{producto_id, cantidad, tipo_precio?=a|b|c}` and price from `precios_productos` (`VentaService::precioLista()`); any client `precio` is ignored. Discounts only with `descuentos.aplicar`. Sales validate stock in the depot.
- Business logic is shared with the web through `VentaService` (incl. `anular()`), `CotizacionService`, `CompraService`, `TrasladoService`, `ProductoService` — never duplicate it in API controllers.
- Deletes are soft (`estado = inactivo`) for productos, clientes, proveedores, depósitos (depósito refused if it has stock); categorías are hard-deleted (products set to NULL).
- Legacy API defects fixed: categorías used a nonexistent table, cotizaciones joined `customers`, compras/traslados used invalid columns/enums, several routes pointed to unimplemented methods, `usuarios/perfil` leaked the password hash and token, 2FA was bypassed.

## Views

Plain PHP, converted mechanically from the legacy engine:

| Legacy | CI4 |
|---|---|
| `View::layout('app')` | `$this->extend('layouts/app')` |
| `View::section('x')` / `View::endSection('x')` | `$this->section('x')` / `$this->endSection()` |
| `View::yield('x')` | `$this->renderSection('x')` |
| `View::e(...)` | `esc(...)` (null-safe) |
| `View::csrf()` | `csrf_field()` |
| `View::include('a.b', $d)` | `echo view('a/b', $d)` |
| `View::isActive(...)` | `is_active(...)` (app_helper) |
| `\App\Core\Auth` / `ModuleManager` | `\App\Libraries\...` |
| `Router::url('/c?...')` | `base_url('c?...')` |

When converting with a script: **never use `sed` for patterns with backslashes** (GNU sed treats `\L`, `\E` in replacements as case-conversion), and **never write a file when `preg_replace` returns null** — a failed regex once emptied every view. Data rows are arrays (`$row['campo']`), never objects.

## PWA (`/m`)

Same design as the sibling `arango` app. Static files in `public/movil/` (not `public/m/`, a real folder would shadow the route on Nginx). `sw.js` and the manifest are served by `MovilController` at `/m/sw.js` and `/m/manifest.webmanifest` so the service-worker scope is `/m/`. Bump `CACHE_NAME` in `public/movil/sw.js` and `?v=` in `app/Views/layouts/movil.php` when `app.css`/`app.js` change. The SW caches `/movil/*` by exact URL (with `?v=`, fetched with `cache: 'reload'`) — it used to match with `ignoreSearch` and served a stale app.js ("desglose no definido" on one phone); the layout also reloads once if `desglose` is missing. Login posts to `/login` with `_origen=movil`.

POS `/m/vender` (`movil/vender.php`, all client-side JS posting to `/ventas/procesar`): list ordered by store sales of the last 30 days (`/m/api/productos?orden=vendidos`) with category chips; camera scanner (`Escaner`) and Enter from a USB/Bluetooth reader go through `agregarPorCodigo()` (exact match on a presentation barcode `productos_unidades.codigo_barras` adds that presentation, then product code/barcode, then single result); cash quick buttons (Exacto + next bills); payment `MIXTO` (pagos[] with amounts, change only from cash — `VentaService` removes the excess from EFECTIVO); discount on the total ($ or %) only with `descuentos.aplicar`. The cart is saved in `localStorage` (`pos_carrito_{user}_{deposito}`) on every change and restored on load; "ventas en espera" live in `pos_espera_{user}_{deposito}` (per phone). Restoring always re-fetches products with `/m/api/productos?ids=` so price/stock/presentations are current; the saved cart is cleared right after a successful sale. `VentaController::procesar` rejects discounts (line + global) above `maxDescuentoPct()` (`companies.pos_desc_gerente` with `descuentos.aplicar`, else `pos_desc_cajero`) for web and PWA.

Create product `/m/productos/nuevo` (`productos.crear`: admin, gerente, encargado): same `ProductoService::crear` as the web; auto code by category (`/api/inventario/siguiente-codigo`), barcode via the browser `BarcodeDetector` (button hidden if unsupported), photo reduced, initial stock only into the active depot (kardex "Stock inicial") plus `minimo`/`ubicacion` there; other depots get 0. Product sheet `/m/productos/{id}` (`MovilController::producto`): price, presentations, stock per depot of the user's branches, last 15 kardex rows and lots of the active depot, 30-day sales, entrada/salida sheet. Edit `/m/productos/{id}/editar` is a **partial** update (`guardarProducto`): nombre, códigos, categoría, marca, proveedor, costo, precio A, estado, photo (camera), plus `minimo`/`ubicacion` of the active depot — it never sends `maneja_lotes`, precios B/C or descripción. Presentations (caja, bulto…) are edited there too (`pres[n][unidad_id|nombre|factor|precio]` + `pres_enviado`, `MovilController::guardarPresentaciones`: updates in place keeping `unidad_id`, inserts new, deletes removed — unlike the web's delete-and-reinsert) (the web `actualizar` rewrites all fields, so don't reuse it from mobile). Product photos: `public/assets/js/foto-producto.js` (`FotoProducto.reducir()` → JPEG ≤1200 px before upload; `webcam()` modal on desktop; `conectar()` for `[data-foto]` blocks) used by the web partial `partials/foto_producto.php` (top of create/edit, field `imagen_principal`) and the PWA: the photo is changed only from edit (web and PWA); tapping it on `/m/productos/{id}` or the web detail `inventario/{id}` opens a full-size viewer (modal). `/m/ventas?venta=ID` opens the sale detail sheet (used by Inicio and the post-sale ticket). Still sending users to the web: sale cancel/print, client detail/credit limit, stock movements and purchases of lot-managed products.
